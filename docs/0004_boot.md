# 4. ブート

OS開発の最初、まずは起動処理からになる。

## 方式

ブート処理の方式はいくつか選択肢がある:

1. OpenSBIやRustSBIなどの既存のSBI実装を利用する (例: Linux,FreeBSD)
2. ファームウェアなし(-bios none)でM(Machine)モードで起動 (例: xv6-riscv)
3. 小さなSBI実装を自作する (例: Zephyr,NuttXの内蔵SBI)

SBI(Supervisor Binary Interface)については説明しておこう。SBIはファームウェアがOSに機能を提供するときのインターフェースをまとめた規格で、この規格でやりとりをすればOS側はファームウェアごとに対応するコードを書く必要がなくなる。

SBIはとても便利ではあるのだが、今回はOSが直接Mモードで起動する方式で進めていく。

## 起動処理

QEMUは `-bios none` のときリセットベクタ `0x1000` で `a0 = mhartid`、`a1 = DTB`(Device Tree Blob: ハードウェアの構成情報) のアドレスをセットしてから `0x80000000` にジャンプとなる。なので、OSはこのアドレスから処理を開始することになる。

### リンカスクリプト

一番最初のリンカスクリプトはこのようになる。

```ld
ENTRY(entry);

SECTIONS
{
    . = 0x80000000;

    .text : {
        KEEP(*(.text.boot));
        *(.text .text.*);
    }

    .rodata : ALIGN(16) {
        *(.rodata .rodata.*);
    }

    .data : ALIGN(16) {
        *(.data .data.*);
    }

    .bss : ALIGN(16) {
        *(.bss .bss.*);
    }

    .stack(NOLOAD) : ALIGN(16) {
        . += 4096;
        PROVIDE(__stack_top = .);
    }

    .comment          0 : { *(.comment) }
    .riscv.attributes 0 : { *(.riscv.attributes) }
    .symtab           0 : { *(.symtab) }
    .strtab           0 : { *(.strtab) }
    .shstrtab         0 : { *(.shstrtab) }

    /DISCARD/ : {
        *(.eh_frame);
    }
}
```

要点だけつまんでいこう。

- 上述したように、`0x80000000` で開始できるように開始位置のセクションを固定する必要がある。`.text.boot`というシンボルがここにくるようにしている。
- `.eh_frame` というセクションがカーネルのバイナリに含まれないようにしている。これを書いておかないと、ldcが生成したバイナリは先頭に `.eh_frame` を配置してしまう。`.eh_frame` 自体は例外処理にかんするもので、OS開発で利用することはないので無視してかまわない。

### 最初のプログラミング

起動処理を確かめたいだけなので、最初のプログラムではほとんどなにもしない。ただ `wfi` 命令で割り込みをまつだけである。

```d
import ldc.attributes : naked, section;
import ldc.llvmasm : __asm;

@section(".text.boot")
extern(C) @naked void entry() @nogc nothrow @system
{
    __asm(`
    1:  wfi
        j 1b
    `, "");
}
```

大事な点をあげておこう:

- リンカスクリプトにあわせて、`.text.boot` セクションに配置することでOSの開始位置(エントリポイント)がこの関数にくるようにする。
- `@naked` をつけることで関数のprolog/epilogの出力を抑制している。まだspになにも設定していないのでスタックフレームを作るようなコードが生成されてしまうと壊れる。

nakedについてはLDCではより注意が必要だ。
ためしにこんなコードをコンパイルしてみよう。

```d
// 内容についてはまだ理解しなくていい
import ldc.attributes : naked;
import ldc.llvmasm : __asm;

@naked void f(uint x)
{
    __asm("csrw sepc, $0\n sret", "r", x);
}
```

LDCで壊れたIRを作ってしまうため、このコードはLLVMのエラーになる。

```
cannot use argument of naked function
i32 %0
Load operand must be a pointer.
  %2 = load i32, i32 %0, align 4
LLVM ERROR: Broken module found, compilation aborted!
```

「naked関数では関数の引数を使ってはいけない」という知識があれば読み解くことはできるが、初見ではコンパイラがクラッシュしたようにもみえてしまう。

clangでは同じ書き方をフロントエンドで弾き、きちんとエラーメッセージを出している。

```c
__attribute__((naked)) void f(unsigned x) {
    __asm__ volatile("csrw sepc, %0\n sret" :: "r"(x));
}
```

```
error: parameter references not allowed in naked functions
```

### ビルド

OS開発のときは、コンパイル時にたくさんのオプションをつけることになる。

```
ldc2 \
	-mtriple=riscv64-unknown-none-elf \
	-mattr=+m \
	-code-model=medium \
	--checkaction=halt \
	--relocation-model=static \
	--transition=tls \
	-betterC \
	-c \
	-od=build \
	-op kernel/*.d
```

各オプションをみていこう

- `-mtriple=riscv64-unknown-none-elf`: ターゲットトリプル(トリプルという名前は歴史的経緯だ)では、ターゲットとなるアーキテクチャやOSなどを指定する
- `-mattr=+m`: RISC-Vの拡張で利用したいものを指定。`+m`は整数の乗算・除算
- `-code-model=medium`: アドレス空間 (ref: https://docs.riscv.org/reference/abi/v1.0/riscv-elf-code-models.html#5-1-2-medium-any-code-model)
- `--checkaction=halt`: `assert(0)` は即haltする。RISC-Vの場合、`unimp` 命令(不正命令)になる。
- `--relocation-model=static`: PICを使わない
- `--transition=tls`: TLSを利用しているコードはその情報を出す。TLS領域の設定はしてないので使わないよう警告を出す意図。
- `-betterC`: ランタイムや標準ライブラリにリンクしないように
- `-c`: オブジェクトファイルの生成まででとどめて、最終的なカーネルのバイナリの生成は別にリンカコマンドで行う

リンカはこうなっている:

```
ld.lld \
	-T kernel/kernel.ld \
	--orphan-handling=warn \
	-o $@ \
	$$(find build -name '*.o')
```

上述のリンカスクリプトを使うくらいでめぼしいことはしていないが、`--orphan-handling=warn` で扱いを決めていないセクションについては警告を出すようにしている。

生成したカーネルのバイナリをみてみよう。

```console
$ llvm-objdump -dw build/kernel.elf

build/kernel.elf:       file format elf64-littleriscv

Disassembly of section .text:

0000000080000000 <entry>:
80000000: 73 00 50 10   wfi
80000004: 6f f0 df ff   j       0x80000000 <entry>
```

ちゃんと `entry` 関数が `0000000080000000` に配置されていることが確認できる。

ところで、wfi命令を待ち受けるだけなら以下のようなコードでもよいんじゃないの?という疑問が出てくると思う。

```d
@section(".text.boot")
extern(C) @naked void entry() @nogc nothrow @system
{
    while (true)
        __asm("wfi", "");
}
```

このコードで出力されるバイナリはこうだ:

```
0000000080000000 <entry>:
80000000: 6f 00 40 00   j       0x80000004 <entry+0x4>
80000004: 13 05 00 00   li      a0, 0x0
80000008: 63 1a 05 00   bnez    a0, 0x8000001c <entry+0x1c>
8000000c: 6f 00 40 00   j       0x80000010 <entry+0x10>
80000010: 73 00 50 10   wfi
80000014: 6f 00 40 00   j       0x80000018 <entry+0x18>
80000018: 6f f0 df fe   j       0x80000004 <entry+0x4>
```

なんでこんなことになるのかというと、これは最適化を行っていないためだ。
LLVM-IRをみるとどういう意図でこういうバイナリが吐かれているかがわかりやすい。

```
; Function Attrs: naked
define void @entry() #0 section ".text.boot" {
  br label %forcond

forcond:                                          ; preds = %forinc, %0
  br i1 true, label %forbody, label %endfor

forbody:                                          ; preds = %forcond
  call void asm sideeffect "wfi", ""(), !srcloc !1
  br label %forinc

forinc:                                           ; preds = %forbody
  br label %forcond

endfor:                                           ; preds = %forcond
  unreachable
}
```

このバイナリについて逐一解説するつもりはないが、`a0` レジスタを勝手に使っていることに気がついてほしい。`naked`関数内ではそもそもprologを設定していないのでインラインアセンブリしか書いてはいけないのだが、もうひとつ問題なのはスタックポインタを設定していない状態でローカル変数をスタックに退避(spill)するようなコードが吐かれてしまうことだ。そうすると不正な書き込みが起こってカーネルはクラッシュしてしまう。そこで、次はスタックポインタを設定するコードを書こう。
(そして、なぜ世のOS開発者が初学者向けの資料であってもまず最適化フラグをつけるようにしているのかがわかったと思う。本書もこれ以降最適化フラグ `-O2` を付与して進めていく)。

entry関数をスタックポインタをセットするように書き換えるとこのようになる。

```d
import ldc.attributes : naked, section;
import ldc.llvmasm : __asm;

@section(".text.boot")
extern(C) @naked void entry() @nogc nothrow @system
{
    __asm(`
        la sp, __stack_top # spに__stack_topのアドレスをセット
        csrr a0, mhartid   # 自身のhartidをa0にセット
        slli t0, a0, 12    # a0 << 12: 各hartごとに4096バイトのスタック領域をあてるために
        sub sp, sp, t0     # ここでhartごとにスタック領域割り当て
        j kmain            # カーネルのメイン関数にジャンプ
    `, "");
}
```

リンカスクリプトの項で `__stack_top` をスタックの一番上のアドレスに宣言していたことを思い出してほしい。RISC-VではABIとしてスタックは下位のアドレスの方向に伸びる決まりがあるので、この仕組みは決めうちだ。

次にhartid(hardware thread id)というのは、コアやSMTごとに割り振られるIDになる。ようはマルチコア環境で動かす場合はスレッドごとに個別のスタック領域が割り当てられるようにしている。
今回はqemuに `-smp 1` を指定して1コアでしか動かさないように固定しているので意味がある処理になってはいないが、将来的に複数スレッドでOSを動かすよう拡張する際は留意しておくとよい。

ジャンプする先のkmain関数はこのようになっている:

```d
module kernel.main;

import ldc.llvmasm : __asm;

extern(C) noreturn kmain() @nogc nothrow @system
{
    while (true)
        __asm("wfi", "");
}
```

最適化フラグを与えているのでけっきょく生成されていないのだが、スタックポインタをセットしたのでインラインアセンブリ以外の処理を関数内部に書けるようになった。

### Mモード -> Sモード への移行

そもそもMモードとかSモードとかなに?って話がある。

CPUは特権レベルというものがあり、「今どこまでの操作が許されてるか」というのがモードによって決まっている。RISC-Vだと M(Machine)モード/S(Supervisor)モード/U(User)モードの3つが定義されている。じゃあこれはできることがなにが違うのか、というと、モードによって触ることができるCSRや使える命令、アクセス可能なメモリ領域が違ってくる。

CSR(Control and Status Register)というのは、CPUの設定とか状態を読み書きするための特別なレジスタのことで、このレジスタをいじることで特権モードにおける振る舞いを変更することができる。

CSRや命令はprefixでアクセス可能な最低の特権レベルを表す(例: mstatusとsstatus)。

こうやって権限を分離することでなにがうれしいかというと、たとえばユーザモードのコードでやらかしても影響範囲を限定できる。

というわけで、kmainをSモードで起動する前に以下のような処理を挟む必要がある:

- mretで飛ぶ先をkmain(カーネル本体のエントリポイント)に設定
- Sモードでのメモリアクセスを許可
- ページングを無効にした状態でSモードに入るように設定
- 例外と割り込みをSモードに委譲
- 実際にSモードへ切り替える

このへんの処理をentryに書いてもよいが、せっかくD言語を使っているので関数に切り出そう。

```d
// DTBはブートROMや前段のブートローダがa1で渡すことを想定している。
// 今のところはQEMUでしか動かさないのでこのままで問題ない。
extern (C) void start(ulong hartid, void* dtb) @nogc nothrow @system
{
    // MPP: Machine Previous Privilege
    // Sモードにセットする
    clearCsr!"mstatus"(MSTATUS_MPP_MASK);
    setCsr!"mstatus"(MSTATUS_MPP_S);

    // mretで飛ぶ先をkmain関数にする
    writeCsr!"mepc"(cast(ulong) &kmain);

    // Sモードでのメモリへのアクセスを許可する
    writeCsr!"pmpaddr0"(0x3f_ffff_ffff_ffffUL);
    writeCsr!"pmpcfg0"(PMP_A_TOR | PMP_R | PMP_W | PMP_X);

    // satp = 0: ページング無効にした状態でSモードに入る
    writeCsr!"satp"(0);

    // 割り込み・例外をSモードに委譲する(書き込めないビットは無視される)
    writeCsr!"medeleg"(0xffff);
    writeCsr!"mideleg"(0xffff);    

    // Sモードに切り替え
    __asm("mret", "{x10},{x11}", hartid, dtb);
}
```

## まとめ

まとめとして、最終的なビルド時のMakefileをはっておこう。

```
build/kernel.elf: kernel/*.d kernel/kernel.ld
	mkdir -p build
	ldc2 \
		-mtriple=riscv64-unknown-none-elf \
		-mattr=+m \
		-code-model=medium \
		--checkaction=halt \
		--relocation-model=static \
		--transition=tls \
		-betterC \
        -O2 \
		-c \
		-od=build \
		-op kernel/*.d
	ld.lld \
		-T kernel/kernel.ld \
		--orphan-handling=warn \
		-o $@ \
		$$(find build -name '*.o')

run-qemu: build/kernel.elf
	qemu-system-riscv64 \
		-machine virt \
		-bios none \
		-nographic \
		--no-reboot \
		-smp 1 \
		-d int,guest_errors -D qemu.log \
		-kernel $<
```

`make run-qemu` でQemuが起動して、警告がなにもでずにコンソールが入力待ちになっていれば成功。`C-a x` (Ctrlキーとaキーを同時押ししたあと、xキーを押す)でQemuを終了させる。
